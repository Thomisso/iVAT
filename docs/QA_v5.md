# QA v5: rychlejší CI, ruční doklady, obnova přístupu a nová identita iVAT

**GitHub issue:** [#159](https://github.com/Thomisso/iVAT/issues/159) — ready-for-agent.

**Stav:** schválená specifikace podle uzavřeného grill-with-docs a závěrečného potvrzení uživatele. Testovací rozhraní byla součástí potvrzeného zadání: stávající Playwright scénáře a aplikační integrační testy proti izolované lokální Supabase. Publikace specifikace není implementací ani změnou produkce. Na následný výslovný pokyn uživatele je doplněna optimalizace GitHub Actions a testovací náročnosti jako priorita 0 před všemi dosavadními úkoly QA v5.

## Problem Statement

GitHub Actions se při vývoji spouštějí často a dlouhé CI prodlužuje každou iteraci i celkovou spotřebu runner času. Rutinní testy navíc vytvářejí velké počty Companies a účtů, přestože uživatel očekává produktové nasazení v řádu desítek Companies. Potřebuje nejprve zrychlit a zúžit zbytečnou práci CI při zachování důležitých regresních a release kontrol.

Uživatel nemá spolehlivou cestu ke změně nebo obnově hesla. Produkční pilot nemá zprovozněné SMTP, takže nemůže doručovat obnovu hesla ani e-mailové pozvánky. Administrátor současně potřebuje pozvat konkrétního člověka zkopírovaným odkazem bez odesílání zprávy ze systému. Přihlášení nabízí nefunkční veřejnou registraci a nenastavené Google přihlášení. SuperAdmin se objevuje mezi aktivními uživateli organizace, přestože jeho přístup vyplývá z platformní role.

Aplikace předpokládá nahraný zdrojový soubor a předchozí úspěšné vytěžení. Uživatel proto nemůže založit doklad jen ručním zadáním a při selhání vytěžení nebo rozdělení souboru může skončit bez možnosti údaje doplnit či položku vědomě vyloučit. Potřebuje zachovat původní soubor, dohledatelnost změn a stejná pravidla schválení i u ručně zadaných údajů.

Není spolehlivě rozlišeno schválení dokladu, jeho skutečné zahrnutí do výkazu, blokující chyba a pouhé upozornění. Hlášený produkční příklad Orlen ukazuje rozpornou informaci o zahrnutí; přesná příčina ještě nebyla reprodukována. Chybějící režim DPH nesmí dovolovat schválení. Uživatel potřebuje opravit režim z nabídky a vidět výsledný řádek přiznání a oddíl kontrolního hlášení také v kontrolním exportu. Kontrolní hlášení opakuje oddíly místo jednoho souvislého bloku pro každý oddíl.

Současná identita neodpovídá novému PDF návrhu loga a přihlášení. Aplikace navíc neukazuje spolehlivě verzi skutečně nasazeného release a exportní XML deklaruje starou pevně zadanou verzi.

## Solution

**[Priorita 0 — optimalizace CI #181](https://github.com/Thomisso/iVAT/issues/181):** před další implementací QA v5 změřit skutečné náklady workflow/testů a dodat zkrácení doby do výsledku i celkového runner času. Použít malé, účelné fixture, omezit opakovaný setup, rušit překonané PR běhy a rozlišit levné dokumentační/draft kontroly od úplného ověření změn připravených k merge a přesné main revize pro release. Zachovat pokrytí skutečných hranic stránkování, bezpečnosti a účetních pravidel; předpoklad desítek Companies není nový produktový limit.

Zpřístupnit změnu vlastního hesla a obnovu zapomenutého hesla přes jednorázový e-mailový odkaz včetně funkčního MFA obnovení. Zprovoznit spravovanou e-mailovou schránku Roští Small pro odesílatele iVAT na noreply@ivat.cz, ponechat doménu i DNS u WEDOS, doplnit poštovní DNS a prokázat skutečné produkční doručování.

Administrátorovi nabídnout dvě akce: „Pozvat uživatele“ odešle e-mail, „Vygenerovat link“ vytvoří pozvánku bez e-mailu. Čekající pozvánky umožní stejný platný odkaz znovu kopírovat, zrušit nebo nahradit novým. Nový User nastaví heslo, existující použije své přihlašovací údaje.

Umožnit ruční založení Document bez Source File a doplňování neúplných údajů. Pro každé ruční uložení je povinné platné DUZP; ostatní údaje lze doplnit před schválením. Source File lze přiložit později a samostatnou potvrzenou akcí spustit AI Extraction nahrazující aktuální hodnoty novou verzí při zachování historie. Selhání Splitu či Extraction vyřeší ruční zpracování nebo zdůvodněné, vratné vyloučení.

Sjednotit informaci o skutečném zahrnutí do výkazů, vynutit režim DPH před schválením, zpřístupnit jeho výběr a zobrazit odvozené řádky a oddíly. Seskupit kontrolní hlášení v HTML i PDF. Novou světlou identitu podle PDF promítnout do přihlášení, souvisejících obrazovek a společných prvků aplikace; přidat přesnou release verzi. Veřejnou registraci uzavřít a její návrat evidovat samostatně v backlogu.

## Implementation Decisions

- **First delivery and measurement:** CI optimization is priority 0 and an explicit prerequisite of every previously unblocked QA v5 task; those prerequisites gate all existing work transitively. It starts from the current implementation and must not wait for the private-account-fixture or other new-feature tickets. Record historical/current workflow frequency, queue time separately, job/step durations, setup versus test costs and summed runner time. Compare like runner classes, application revisions and cache conditions; demonstrate reduced heavy executions and improved wall time plus total runner cost for representative full verification. The user did not set a numeric SLA, so establish measured budgets rather than inventing a promised percentage.
- **Proportionate triggers:** docs-only PRs avoid database/browser/container-runtime stacks while producing a stable meaningful gate. Draft PRs get quick inexpensive checks; ready-for-review and subsequent relevant ready-PR commits receive complete required checks for the latest revision. Known safe filtering must include runtime assets, dependencies, migrations and workflows in its impact model, with a full-check fallback for uncertainty. Keep complete exact-main-commit CI and deployment evidence for release; docs/draft success, skipped jobs or a different revision are not substitutes. Avoid pending required checks when filtering, and preserve failure propagation.
- **Waste and fixtures:** cancel obsolete test runs within the same PR/workflow and clean temporary resources without cancelling other PRs, production deployment or required release evidence. Profile duplicate setup and builds before applying caches or artifact reuse; retain correctness on a cache miss and exact-revision provenance. Reduce excessive Company/Auth inventory with smaller data, efficient bulk setup, cleanup and immutable shared inputs while assertions still cross real application/Auth/RLS boundaries. Preserve multi-page regressions with a small supported page size where it reproduces the real behavior, or the minimum efficiently seeded production-boundary case where it does not. Dozens of Companies is an expected operating scale, not a cap on Companies, Documents, Users or platform-wide Organizations. Do not delete a semantic regression merely because its current fixture is large or introduce unsafe concurrency on a shared mutable database stack.
- **Authority and boundaries:** keep Organization as tenant, Company as reporting subject and existing Role scopes. Extend existing application services, authenticated actions, Auth adapters, database commands and reporting preparation. No new public integration API or parallel workflow engine is required. PostgreSQL remains the authority for tenant access, role checks and business invariants under ADR-0008. Preserve audit limits for User personal data under ADR-0009.
- **Release identity:** carry the exact deployed release tag and revision from the existing release/image provenance into application build/runtime metadata. Do not fetch the latest GitHub release at request time or trust a stale package version. Show the same release in login and account menu. Development uses „Vývojová verze“. New exports already carrying software-version metadata use the actual generator version. Previously archived XML retains its exact bytes, hash and original metadata; a deployment never rewrites it. Existing report-generation and finalization identities remain separate from software version.
- **Personal credentials:** add password change and recovery to existing personal security/authentication surfaces. A normal change requires the current password; initial invited password setup and token-authorized recovery are distinct flows. Recovery links are single-use and expire after one hour. Show a generic request response regardless of account existence and helpful invalid/used/expired states. Keep the current session after success and terminate other sessions using Auth's supported behavior. Do not promise immediate invalidation of every already-issued access token; token expiry and session revocation are distinct.
- **MFA recovery:** preserve mandatory/enforced MFA policies. Email alone cannot remove MFA. Support a valid authenticator or, for the confirmed lost-authenticator scenario, email recovery plus a single-use backup MFA code followed by establishing a replacement factor. The recovery session must remain restricted until required MFA is restored. Existing application-only recovery state does not satisfy Auth's actual elevated-session requirement; integrate and verify the full Auth operation. Do not silently unenroll MFA or expose tenant data as a workaround. Lost email plus no usable second factor or recovery code is outside this self-service scope.
- **SMTP delivery:** use a managed Roští Small mailbox for noreply@ivat.cz and its authenticated, encrypted SMTP connection from the existing Auth service. The agreed published tariff was 60,50 Kč including VAT monthly, 1 GB, 50 outgoing messages/hour and 100/day. Keep registration, nameservers and DNSSEC at WEDOS. Take exact SMTP, MX, SPF, DKIM and DMARC values from the activated mailbox service; do not blindly reuse deprecated application-SMTP credentials or a historical shared DKIM key. Merge existing senders into one SPF record when needed. Preserve website DNS/routing. Keep credentials in private runtime configuration. Validate configuration, DNS authentication and actual invitation/recovery delivery in production; merely filling environment variables or capturing local mail is insufficient.
- **Email-token separation:** a one-hour Auth recovery token must not shorten the seven-day Invitation lifecycle. Likewise, a persistent copied Invitation must not depend on an expired short-lived Auth token generated at creation. Use server-authorized account provisioning and token verification appropriate to the separate lifecycles while public signup remains disabled. Opening a landing page, following a preview or email-scanner GET must not consume access; require the explicit user action. Preserve trusted callback origins and existing redirect allowlisting.
- **Invitation actions and state:** „Pozvat uživatele“ creates and delivers email; „Vygenerovat link“ creates the same scoped Invitation without sending email. Bind it to email, target and Role; Organization allows Administrator, Company allows Administrator or User. Never grant SuperAdmin through tenant invitations. Preserve new/existing identity branches, including an existing Auth User without a Membership. Pending invitations expose email, Role, lifecycle state, expiry and the same copyable valid link across reloads. The current hash-only representation cannot reconstruct that link; adapt token handling so repeated authorized copying works, while restricting sensitive link material to authorized administrators and keeping it out of logs and audit payloads.
- **Invitation renewal and cancellation:** invitation acceptance, cancellation and replacement must be authoritative and single-use under concurrent actions. Copying does not extend expiry. Cancellation invalidates the old link; replacement invalidates it and creates a new seven-day link. Link generation and replacement do not send mail implicitly; the email action is explicit. Invalid, expired, cancelled, replaced and already-used links cannot produce sessions or Memberships beyond their valid scope. Existing Users keep their password; only a genuinely new User chooses an initial password.
- **Closed public registration:** remove the login registration entry and close direct public signup actions/routes as well. Leave internal Company creation/management and administrator-issued onboarding operational. Unconfigured Google login and its unused separator disappear. A later configured Google provider must not become a backdoor to public User/Organization creation. Repairing and reopening public signup is the separate backlog item referenced below.
- **SuperAdmin presentation:** omit platform SuperAdmins from active Organization user lists and counts, including identities with historical Memberships. Preserve membership-independent platform authority under ADR-0014, real actor attribution, mandatory MFA and ordinary business safeguards. Avoid creating synthetic Memberships during provisioning. Hiding a row must not delete Organizations, Companies, other users or tenant data, and must not alter ordinary Administrator/User scopes.
- **Visual identity:** the supplied six-page PDF supersedes the former brand mark, palette and authentication composition. Use the blue rounded iV mark with yellow dot, matching wordmark and favicon/app-icon assets. Apply the light desktop and mobile login references, a coherent frame for invitation/recovery/security flows, and shared application styling from page six. Retain workflows, navigation destinations, responsive behavior, accessibility and CS/EN. The PDF's registration and Google examples are overridden by the confirmed functional restrictions. Desktop background document art is decorative, not fabricated live confidence or source evidence; simplify it according to the mobile reference. Continue the existing typography system and semantic states. No dark theme or theme switcher is introduced.
- **Source-independent Document:** make the Source File association optional and adapt creation, review, lists, queries, viewing, exports and file-dependent operations accordingly. A manual Document belongs directly to the Company and records its real author/time; do not fabricate a Source File, upload, page range or Import Date. Create its first User-authored immutable Extraction Version, preserving ADR-0005. Reuse NeedsReview semantics rather than treating a saved draft as approved. Preserve support for existing file-backed Documents and real source ranges.
- **Manual-save minimum:** every manual save of structured data requires a valid Tax Point Date. A selected Reporting Period cannot replace it. Other business fields may remain incomplete; entered values must have valid format. Draft validation must allow missing amounts and unfinished Rate Breakdown, including an unfinished Credit Note, while approval enforces complete domain rules. Do not infer DUZP from a chosen period. An incomplete AI result can still be preserved for review, but its manual correction must supply DUZP before saving. Reasoned exclusion is not a structured-data save and remains possible without DUZP, so the new requirement creates no fresh dead end.
- **Periods and locks:** keep ADR-0012 period assignment and valid incoming Deferred Claim unchanged. Do not introduce a provisional reporting period or arbitrary outgoing override. Preserve a first manual draft when its DUZP points into a locked period, as the first AI result can be preserved, but refuse assignment, approval or changes to that locked report until its normal resolution. Existing locked Documents cannot be edited, reprocessed, reattached or returned to review without explicit authorized unlock. Draft preservation is a narrow first-version rule, not a general Period Lock bypass.
- **Later source and AI:** attach a real Source File to the same manual Document outside a Period Lock, with the appropriate actual page/row selection when relevant. Attachment alone preserves data, identity, history and approval and starts no AI. Explicit AI action warns about replacing current structured values, withdrawing any existing approval and requiring fresh human review; confirmation authorizes Return to Review and Extraction. Successful AI creates a new immutable version and consumes the normal successful AI allowance. Failure preserves the last manual data and history without automatically restoring approval. Manual entry, correction, failed AI calls and technical retries do not consume allowance.
- **Manual recovery and Split:** expose manual processing and reasoned exclusion without requiring a prior successful Extraction Version or a retry-only dead end. A failed Source File before Split can define multiple Documents by PDF page ranges or Excel sheet/row ranges; an image produces one Document. Preserve original bytes and validate actual boundaries. Manual Split starts manual data entry rather than automatically enqueuing AI. Before Documents exist, exclusion resolves the Source File without creating a fictitious Document; afterwards, act on the concrete Document. Exclusion requires a short reason, retains originals/history, is visible in readiness and is reversible outside locks. Preserve audit and existing authorization/retention rules.
- **Race safety:** manual takeover, late AI completion, duplicate retries, Split completion, exclusion and cancellation must not race into duplicated Documents or overwrite a newer human version. Invalidate superseded job requests/reservations and use the existing authoritative/idempotent processing boundary. Failed or stale work remains diagnosable; it does not consume successful-extraction allowance or silently restore an old status.
- **VAT classification:** expose the VAT Regime dropdown already grounded in supported regimes: domestic, domestic reverse charge, EU acquisition of goods, EU received service and other/manual classification, plus an empty undetermined option. Missing regime can be saved when DUZP is valid, but is an explicit blocking finding for approval and readiness. Unsupported „other“ is not made reportable by selecting it. Keep deterministic mapping of confirmed VAT Regime, Direction and Rate Breakdown to VAT Return lines and Control Statement sections under ADR-0003. Do not introduce direct line/section overrides or free text. Present applicable derived mapping clearly and explain when no supported mapping can be derived.
- **Truthful inclusion:** preparation/query results shared by document detail, lists, readiness and control export must distinguish review/approval, supported derived mapping, actual inclusion in the selected current report and exclusion reason. An Approved Document is necessary but not sufficient for inclusion. Advisory findings such as bank checks do not become exclusion merely by appearing on an attention sheet. A saved report snapshot must be identified separately from live changed data, preserving existing stale-snapshot/finalization behavior. Show available derived mapping for incomplete or excluded work as proposed mapping alongside the reason, without claiming it was counted; if it cannot be derived, show why rather than inventing a value.
- **Control Statement grouping:** render one block/table per nonempty supported section in order A.1, A.2, A.4, A.5, B.1, B.2, B.3, with its entries and totals, consistently in HTML and PDF. Preserve existing per-entry records, A.5/B.3 aggregation, underlying amounts, statutory XML and document drill-down. Grouping is presentation, not a new tax aggregation rule.
- **Orlen diagnosis:** reproduce the reported production contradiction against the actual deployed version and input state before claiming a root cause. Existing approval-only eligibility and control-export attention handling are candidates, not established explanations. ## Out of Scope

- Introducing a product Company-count cap, deleting important regressions solely because their current fixtures are large, weakening required merge/release checks, unsafe parallel execution over a shared mutable database, or unrelated production-performance work.
- Implementing or reopening public registration now; its future design is the separate backlog item referenced below.
- Dark mode, a theme switcher, new navigation architecture or unrelated workflow redesign.
- Direct manual override of VAT Return lines/Control Statement sections, free-text tax classification, new unsupported VAT regimes or changes to existing tax aggregation and Deferred Claim rules.
- Saving manually entered structured data without valid DUZP, substituting a period for it or inventing a date from period boundaries.
- Automatic approval of AI results, destructive replacement of historical Extraction Versions or rewriting archived XML on a later release.
- Removing MFA based on email alone, unrestricted recovery access, changing other Roles' scopes, SuperAdmin impersonation or bypassing Period Locks.
- Deleting financial evidence as part of exclusion, hiding unfinished work as if included, or treating advisory warnings as reporting blockers by default.
- Running a self-hosted public mailserver, migrating the domain/DNS away from WEDOS or introducing a third-party mail provider instead of the agreed Roští mailbox.
- Automatic submission to the tax authority or treating an exported/downloaded file as proof of filing.
- Starting implementation, creating implementation child tickets or opening implementation PRs as part of this spec-publication task.
