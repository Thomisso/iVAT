# GitHub Actions workflow audit — 2026-11-09

## Finding and recommended decision

The present workflow spends substantial time on orchestration and repeated checks. Preserve pull requests, independent review, database isolation and meaningful application coverage. First remove serial dependencies and duplicate work, repair the observed test-fixture races, and make infrastructure tests conditional on their actual inputs. A full application suite is useful before integrating application changes; running the full tracker suite for every unrelated draft/docs change and full production stacks for every docs-only main push is a repository policy choice, not a GitHub requirement.

This is a read-only audit of remote configuration and execution, plus a documentation artifact. It does not modify workflow code, branch settings, billing, tracker state or issue specifications. Existing local edits to AGENTS.md and README.md predate this audit and are preserved. No new Actions run, browser suite or database stack was launched.

## Scope and method

- Source baseline: main `7997422a307cda3bbcc66e39030810b637c4aa65`; inspect [CI](../.github/workflows/ci.yml), [deployment verification](../.github/workflows/deployment-check.yml), [tracker workflow](../.github/workflows/agent-tracking.yml), [profile classifier](../scripts/ci-policy.mjs), [release policy](../deploy/scripts/release-policy.mjs) and the documented [handoff rules](agents/agent-tracking.md#final-checks-handoff-and-delivery).
- Read the latest 100 CI and 100 deployment runs, each spanning 2026-10-31 05:18 UTC through 2026-11-08 11:35 UTC. Fetch every attempt's job/step metadata: 103 CI attempts and 101 deployment attempts. These are matching bounded samples, not the complete repository history.
- Separately read the latest 100 tracker runs, spanning 2026-11-08 08:11 UTC through 2026-11-09 14:09 UTC. One was still running in the snapshot. Its incomplete interval is excluded from duration totals. These tracker totals cover a different interval and must not be extrapolated or combined as the same-period bill.
- Read selected failed job logs and check annotations. Distinguish failed tests, infrastructure/billing refusals and intentional superseded-run cancellations. Final gate failures caused by a failed prerequisite are not separate defects.
- Sum completed, actually started job intervals. For a billing proxy, round each such job interval up to a minute. Exclude skipped jobs and no-step jobs refused before execution. This is an estimate from timestamps, not GitHub's metered invoice. Earlier runs in this sample used the historical browser acceptance configuration; they were inspected as records, never executed. Current-runtime timings below use only the November 8 HTTP configuration.
- Billing API read returned HTTP 404 with a CLI diagnostic that the existing credential lacks the `user` scope. Actual plan, available allowance, billed units and payable total remain unknown. No credential scope was changed.

## Concrete waste and failure evidence

1. **Slow work precedes classification.** `CI profile` runs the whole `test:agent-tracker` suite before calculating docs/draft/full. Both application shards and HTTP acceptance wait on it. A supposedly cheap [draft execution 42353190495](https://github.com/Thomisso/iVAT/actions/runs/42353190495) took 11:45; tracker alone took 10:28. The current docs profile has the same unconditional tracker step. [CI source](../.github/workflows/ci.yml)
2. **Common checks run three times.** Each application shard installs Postman and runs release-policy tests, the real-gh transport simulation, database-type generation, typecheck, lint and a Next build. In the representative PR run, release tests consumed 161 seconds across shards, transport 67, typecheck 71, lint 90 and standalone builds 199. Consolidating these repeated checks models roughly 6–8 runner minutes of gross savings before replacement-job/setup overhead; actual savings must be measured. The three standalone builds plus the HTTP build plus the Docker build make **five application builds** per current full PR/main event. Keep the production-image build's distinct packaging/runtime evidence. [CI](../.github/workflows/ci.yml), [HTTP runner](../scripts/e2e.mjs), [Docker verification](../.github/workflows/deployment-check.yml)
3. **Docs main pushes always select full.** The classifier explicitly returns full for every non-PR event. A direct invocation confirmed `pull_request + README.md → docs`, but `push + README.md → full`. The historical docs-only commit `c4c96a3` changed three Markdown documents and consumed 24:39 wall / about 65:56 summed CI runner time in [42278518096](https://github.com/Thomisso/iVAT/actions/runs/42278518096). That older run used browser acceptance; current main still has the same full-on-push selection but now uses HTTP acceptance. [Classifier](../scripts/ci-policy.mjs)
4. **Documentation appended to an application PR is different.** PR classification uses the entire base-to-head diff. A README-only final commit does not make earlier unmerged application changes disappear. Selecting tests solely from the final commit would lose necessary verification. Safe reuse would need validated relevant-input identity, current target compatibility and explicitly supported evidence transfer; the current tracker deliberately invalidates obsolete exact-revision evidence. [Classifier](../scripts/ci-policy.mjs), [final evidence policy](agents/agent-tracking.md#final-checks-handoff-and-delivery)
5. **Redundant event triggers.** Both test workflows subscribe to every label add/remove and both draft transitions. Even an unrelated label can restart checks on the same revision. PR #252 passed full CI at 11:28, then another [CI run 42476193576](https://github.com/Thomisso/iVAT/actions/runs/42476193576) started at 11:32 on the same head `df0b5cb` and was cancelled after merge. The API run summary does not identify the triggering PR sub-action, so its precise trigger is unproven; the configured label/readiness triggers nevertheless permit this pattern. Keep an eligible PR/push merge check, and handle `ci:full` changes explicitly rather than every label. [CI source](../.github/workflows/ci.yml)
6. **Tracker tests have demonstrated nondeterminism.** Main [42476395666](https://github.com/Thomisso/iVAT/actions/runs/42476395666) failed its first attempt after 13:51 in the tracker suite, then passed the second attempt at the same source revision. The error was `Unexpected end of JSON input` in `trackerFixture.remote()` while a child process updated the synthetic GitHub JSON file. [42465167591](https://github.com/Thomisso/iVAT/actions/runs/42465167591) similarly failed the concurrent Mac-alias test on a partial JSON read, then passed at the same revision. Source has synchronous JSON reads and non-atomic fake-service writes; stabilize that fixture boundary and its synchronization before considering retries. This evidence identifies a test-fixture read failure, not a proven application defect. [Fixture reader](../scripts/tests/support/agent-tracker-fixture.mjs), [fake GitHub writer](../scripts/tests/support/agent-tracker-gh.mjs)
7. **Other failures were real and distinct.** Four November 7 runs failed the large VAT-report scenario with PostgreSQL statement timeout, including [42423409716](https://github.com/Thomisso/iVAT/actions/runs/42423409716); later PR #243 records the measured RPC fix and full passing evidence. [42472078550](https://github.com/Thomisso/iVAT/actions/runs/42472078550) failed a release test fixture with `EACCES`; the final #252 commit corrected Linux fixture ownership. The historical [41807140100](https://github.com/Thomisso/iVAT/actions/runs/41807140100) failed Supabase startup on a bound port, now addressed by port reservations. These do not justify blanket test deletion or classifying every red run as flaky. [PR #243 evidence](https://github.com/Thomisso/iVAT/pull/243), [PR #252 evidence](https://github.com/Thomisso/iVAT/pull/252), [existing CI diagnosis](ci.md)
8. **Billing refusals are not test failures.** Check annotations for [42366242027](https://github.com/Thomisso/iVAT/actions/runs/42366242027) and attempt 1 of [42456642831](https://github.com/Thomisso/iVAT/actions/runs/42456642831) say the job was not started because recent payments failed or the spending limit needed increasing. The annotation does not distinguish those alternatives. Rerunning application tests cannot fix that condition.
9. **Tracker publication adds another queue.** The three issue-triggered runs for new issue #253 were queued serially. The first [42631953238](https://github.com/Thomisso/iVAT/actions/runs/42631953238) ran 4:41; the second [42631953331](https://github.com/Thomisso/iVAT/actions/runs/42631953331) waited 4:48 and ran 5:07; the third started about 9:58 after creation and was still running in the snapshot. This is progress publication, not implementation or application testing. Its two cron expressions offer up to 312 scheduled wakeups/day if all are delivered; actual observed schedules are much less frequent, so 312 is not measured usage. Coalesce passive wakeups and publish changed projections while retaining ordered owned events and the single writer. [Tracker workflow](../.github/workflows/agent-tracking.yml)
10. **Shards are uneven.** In the representative run, shard 2 spent 443 seconds in application tests versus 239/262 seconds in the others; in the latest main attempt the split was 432 versus 189/215. Balance files by measured runtime before adding shards. More shards repeat setup, database startup and rounding; they may shorten elapsed time while increasing cost. [Run metadata](https://github.com/Thomisso/iVAT/actions/runs/42473990714)

## Recommended implementation sequence

### First: preserve application coverage and remove overhead

- Make profile selection a small, fast job. Move tracker tests into a parallel job. Consolidate release/transport checks, typecheck, lint, database-type verification and redundant builds, with explicit failure/cancellation propagation to stable gates. Keep an isolated database for each application shard and HTTP suite. Existing [#247](https://github.com/Thomisso/iVAT/issues/247) already specifies most of this work; do not create a duplicate ticket.
- Fix the partial-JSON races in the tracker test fixtures with coordinated/atomic state publication and deterministic reader/writer synchronization. Run targeted regression and the tracker suite on the fix, rather than treating retry as proof of stability.
- Filter tracker and release-infrastructure suites by their complete dependency sets: tracker source, tests, support files, configuration, workflow, transport simulations, package/toolchain changes and shared dependencies. Ordinary app/docs changes should not run all tracker scenarios. This expands #247's present requirement that tracker remain unconditional; update its acceptance scope explicitly before implementation.
- Classify docs-only main pushes using a verified complete push range. Unknown/missing ranges select full. Keep cheap policy checks and an always-reporting gate for docs-only events. Preserve runtime checks when the complete diff contains application inputs, even if the last commit is documentation.
- Trigger expensive PR work on relevant content/readiness changes and `ci:full`, not arbitrary labels. Keep draft development cheap, and run full application verification once at final readiness. Reserve `ci:full` for intentional early integration evidence; avoid routinely running full on a draft and immediately repeating it on readiness.
- Keep one reviewable PR per coherent deliverable (an integration PR may cover several child tickets). Local commits do not trigger Actions until pushed; batch intermediate commits when useful and avoid pushes that only generate another equivalent full run. Local focused checks remain the implementation feedback loop. Do not repeat an unchanged full local suite after every publication-only event; preserve its exact applicability and rerun after relevant changes.
- Implement [#246](https://github.com/Thomisso/iVAT/issues/246) for tracker wakeup coalescing and changed-only publication. Preserve ordered controller events, recovery receipts and non-cancelling serialization. Treat slower idle freshness polling as a separate policy decision, because current activity promises depend on it.

### Then: introduce verification proportional to risk

| Change | Recommended default | Full verification location |
| --- | --- | --- |
| Pure documentation | Quick policy/link checks; no application DB/image/tracker suite | On next actual application/release candidate when applicable |
| Tracker or release tooling | Relevant infrastructure suite plus cheap shared checks | Corresponding real transport/runtime acceptance before readiness |
| Application draft | Typecheck, lint and fast affected checks | Full application suite at final PR readiness during the first optimization phase |
| UI-only or narrow app change | Later: affected tests plus a small permanent authority/accounting smoke set and relevant HTTP checks | Broader application regression at release; only after dependency selection is validated |
| Accounting, Auth/RLS, migrations, shared infrastructure/dependencies | Full relevant application/security/upgrade coverage before merge | Exact release-candidate production-image/runtime verification as well |
| Production release | Tests and image/runtime acceptance for the exact selected release inputs | Required before deployment; no blind reuse from an unrelated green revision |

Keep authorization, cross-tenant isolation, accounting invariants, immutable history/artifacts and migration/upgrade checks. Audit expensive fixtures for redundant provisioning, but preserve genuine pagination/limit cases. The existing production HTTP suite is relatively short and provides a different signal from application tests; it is not the first candidate for deletion. It still cannot prove visual/client behavior.

Moving full deployment verification from every unrelated PR/main event to deployment-impacting changes and release candidates can save more compute, but changes the current [release verifier](../deploy/scripts/release-policy.mjs): it currently requires successful main-push executions of both workflows at the exact release SHA. Change release evidence collection/validation and docs together; never make a skipped runtime job satisfy a full release requirement. Similarly, selective application testing is a deliberate reduction in pre-merge coverage until dependency selection is proven, not equivalent evidence by default.

### Measurement and acceptance

Measure separately: time to first useful failure, final execution wall time, rounded runner minutes, queue time, retries by root cause, repeated builds/checks, and actual billing when read access exists. Target docs-only checks around one minute and fast draft feedback around a few minutes; these are proposed budgets, not achieved measurements. For full application work, first verify that tracker and application jobs overlap and that shared steps occur once. Compare the same runner class and meaningful equivalent inputs; report setup/cache overhead and every failed attempt. Do not launch many full runs just to benchmark an optimization.

Native API readback in this audit returned `Branch not protected` for classic main protection and an empty result for branch rules applicable to main. The stricter checks discussed here are therefore currently enforced by repository workflow/tracker/release policy rather than an observed native required-check rule. This is a snapshot, not an instruction to merge unchecked changes. Keep PRs as the review surface; simplifying CI does not require direct development on main or abandoning review.

## Official platform constraints

Verified against current primary documentation on 2026-11-09. These are platform facts and design constraints, not measurements of this account's invoices, plan, permissions or repository rules.

### Billing and measurement

- GitHub rounds **each job** up to a whole minute. Standard Linux 2-core x64 runner usage is currently **$0.006 per minute**; Linux slim 1-core is $0.002. Parallelism can reduce waiting while increasing rounded runner usage through repeated setup and short jobs. Use `sum(ceil(job_seconds / 60))` as an estimate for these runners, separately from workflow wall time. [Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)
- Private-repository compute is charged to the repository owner against a shared monthly included compute value, currently $12 on Free and $18 on Pro/Team. These are monetary allowances, not a guarantee of dedicated Actions minutes; other eligible compute can consume the same allowance. Failed attempts and successful retries both consume usage. Actual payable cost requires this owner's billing records. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- Artifact storage is pooled with GitHub Packages and accrues by storage over time. Cache has a separate 10 GB per-repository allowance; configured usage beyond that allowance can be billed. Short retention reduces future storage costs, not prior accrual. Current standard self-hosted runner use is free on GitHub's side, but this does not cover infrastructure or maintenance. [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- The supported personal-account read is `GET /users/{username}/settings/billing/usage?year=2026&month=11` with API version `2026-03-10`; response rows include repository, SKU, quantity, unit rate, gross amount, discount and net amount. It requires enhanced billing-platform access and, for fine-grained credentials, user **Plan: read** permission. Filter to Actions and this repository before reporting; a 403 is an access limitation, not zero spending. The `/usage/summary` variant is public preview. This research did not call either billing endpoint. [Billing usage API](https://docs.github.com/en/rest/billing/usage#get-billing-usage-report-for-a-user)

### Trigger selection and merge gates

- `pull_request` defaults to `opened`, `synchronize` and `reopened`. Label changes, draft transitions and readiness only trigger runs when explicitly selected. Consequently unrelated labels can be excluded from expensive work while retaining an explicit `ci:full` path. Published-release and manual-dispatch events can trigger a separate release verification process; `workflow_dispatch` can be invoked through `gh` and requires the workflow on the default branch. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- Skipping an entire required workflow with `paths`, branch filters or a skip commit message can leave its checks **Pending** and block merging. A conditionally skipped job instead reports success. Keep a small always-reporting gate and let it validate the selected profile's actual prerequisites; a green skipped job alone proves no tests ran. Required checks apply to the current commit, with test-merge/head behavior depending on available checks. [Troubleshooting required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- Current GitHub documentation explicitly says checks from `workflow_dispatch` jobs do **not** satisfy PR required status checks in a branch ruleset, even on the head branch. Required PR verification must use an eligible event such as `pull_request` or `push`. Manual dispatch remains suitable for release-only work. [Troubleshooting required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
- PR requirements, required status checks, freshness and reviews are repository configuration choices. GitHub does not mandate a full application suite for every documentation commit or another full run after every merge. Check actual branch protection/rulesets before changing job names or readiness behavior; keep required job names unique across workflows. A project-specific release verifier may impose stricter evidence than GitHub itself. [Protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

### Cancellation, scheduling and capacity

- A concurrency group permits one running execution; `cancel-in-progress: true` cancels older running work in that group. By default only one pending execution is retained, with newer pending work replacing it. `queue: max` permits up to 100 pending executions and cannot be combined with cancellation. Use cancellation for superseded PR revisions and retain serialized, non-cancelling writes for stateful tracker/deployment operations. Include workflow identity in PR groups to avoid cross-workflow cancellation. [Workflow concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)
- Hosted-job concurrency is account-plan dependent: standard Free/Pro/Team limits are currently 20/40/60 concurrent jobs. Adding shards does not provide unlimited capacity. [Actions limits](https://docs.github.com/en/actions/reference/limits)
- Scheduled Actions can be delayed or dropped under load; the shortest supported interval is five minutes. A cron-based activity monitor has operational latency rather than a hard timing guarantee. Reducing its frequency must also change any promised freshness/detection policy. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)

### Cache choices

- `actions/setup-node` with `cache: npm` caches package-manager data keyed partly by the dependency lockfile. It **does not cache `node_modules`** and still expects `npm ci`. Existing npm caching does not establish that Docker layers or Next build caches are reused. [setup-node source documentation](https://github.com/actions/setup-node#caching-global-packages-data)
- Buildx supports explicit external cache import/export through registry, inline and GitHub Actions backends. A fresh hosted runner needs exported/imported cache to reuse previous-run layers. Inline supports `min`; a registry cache can use `max`. Scope caches by build target where necessary so one target does not overwrite another's cache. Measure build and transfer time before claiming a saving. [Docker cache backends](https://docs.docker.com/build/cache/backends/), [GitHub Actions cache examples](https://docs.docker.com/build/ci/github-actions/cache/)

These facts support changing **when and how often** checks run, eliminating duplicated setup/checks, and retaining checks proportional to changed behavior. They do not establish that a specific iVAT test is redundant or flaky; that requires repository code and actual run/log evidence.
